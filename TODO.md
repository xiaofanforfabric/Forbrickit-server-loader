# Forbrickit — Bukkit bridge TODO

English | [简体中文](TODO.zh-CN.md)

Progress and remaining work for the fourth ecosystem: running Bukkit/Paper plugins on the
unified Fabric + Forge + NeoForge server (`forbric-kernel`, `src/runtime/java/org/cn/xiaofan/bukkit/`).

A method the bridge cannot answer **refuses with a named `UnsupportedOperationException`**, never a
plausible wrong value. So "not adapted" here means "throws something that names itself", which is a
visible, diagnosable gap — not silent breakage.

**Total refused: ~1 294 of ~1 362 bound methods (≈ 95%).**

> **About these two tables.** They measure different things and must not be added up.
> The generated table counts methods of the *bound Bukkit interfaces* (every abstract method a
> `Player`/`World`/… forces this bridge to declare). The hand-written table counts refusal *sites*
> in files that implement Paper's own service interfaces, where some entries are helper overloads
> rather than interface methods. `ForbricBlock` / `ForbricEntity` / `ForbricPlayer` /
> `ForbricWorld` / `ServerImpl` also contain hand-written refusals inside their generated bodies;
> those are inside the first table's columns, not the second's.

That percentage is **misleading on its own** and should not be read as "5% done". The bound
interfaces are enormous (`Player` alone is 632 methods) and most of the remainder is rarely
reached. What matters is the shape of the gap — §2 splits it by how likely a plugin is to need it.
A plugin that only wants commands, permissions, chat and items runs today; one that wants custom
GUI inventories or item names does not.

## 2. What is missing, by priority

### P0 — blocks whole classes of plugins

These stop a plugin from working at all, not just one call.

| # | Gap | Where | Why it matters |
| --- | --- | --- | --- |
| 1 | **`Component` ↔ Adventure bridge** | `ForbricPlayer.sendMessage(Component)` | Every plugin that colours chat, uses hover/click, or calls `sendMessage(Component.text(...))` sends uncoloured plain text today (the `String` overload works). The two object graphs model the same JSON but are not interconvertible without serialise+parse. |
| 2 | **`ItemMeta`** | `ForbricItemStack.getItemMeta/setItemMeta` | Custom names, lore, enchantments, durability, PDC on items. Enormous share of real plugins (shops, kits with names, custom crafting). Needs the Bukkit-component ↔ game-component mapping. |
| 3 | **`Block` mutation surface** | `ForbricBlock` (61 refused) | `setType` works, but `getDrops`, `breakNaturally`, `getState`, block data, `getRelative` do not. World-editing / build plugins need these. |
| 4 | **`Inventory` beyond the player's** | `ForbricInventory` (does not exist) | Chests, hoppers, custom GUIs. Needs the **container layer**: `InventoryView`, `openInventory`, `InventoryHolder`, cursor stack. |
| 5 | **`Entity` beyond a handle** | `ForbricEntity` (148 refused) | Spawning, health, damage, AI, teleport, equipment. Needs entity-lifecycle work on the game side. |

- `ForbricPlayer` odds and ends: statistics, advancements (`discoverRecipes`), `sendEquipmentChange`, custom chat completions, resource packs per-player.

## 4. Design rules this bridge follows

Worth keeping in mind before "just implementing" a method:

1. **Refuse by name, never return a plausible wrong value.** A stub that returns `null` or `0`
   turns "this is not implemented" into a game-play bug far from its cause.
2. **Generated files are overwritten wholesale.** `ForbricPlayer.java`, `ForbricWorld.java`,
   `ForbricEntity.java`, `ForbricBlock.java`, `ServerImpl.java` come from `tools/gen_stub.py`.
   An implementation added to the `.java` alone is **lost on the next regeneration** — it must go
   in `tools/stubs/<Class>.java.in` **and** get a `.table` entry. This has already cost one
   debugging session (permissions reverted to `notYet`, which made players unable to join).
3. **After regenerating, diff the refused-method sets** against `HEAD` — a silent revert is
   invisible otherwise. See §5.
4. **`notYet()` returns the exception; it must be `throw`n.**
5. **`ForbricLog` uses `String.format` (`%s`), not `{}`.**
6. **A live view, not a copy.** Handles read through to the game every call, so a plugin sees
   changes made by anything else.

## 5. How to regenerate and verify

```sh
export JAVA_HOME=~/.local/share/hmcl/java/linux-x86_64/mojang-java-runtime-epsilon
export PATH=$JAVA_HOME/bin:$PATH
export MC_DIR="$HOME/桌面/.minecraft"          # REQUIRED, or ~100 false errors

cd forbric-kernel
./gradlew -q printBukkitApiClasspath > /tmp/cp.txt
python3 tools/gen_stub.py --table tools/stubs/ForbricPlayer.table --classpath "$(cat /tmp/cp.txt)"
```

Then confirm nothing was lost:

```bash
git show HEAD:forbric-kernel/src/runtime/java/org/cn/xiaofan/bukkit/ForbricPlayer.java > /tmp/old.java
# refused = each `throw notYet(` plus the nearest preceding `public ...(` line
# expect: (now - old) empty apart from newly-implemented methods
```

### Build and deploy

```sh
cd forbric-kernel && ./gradlew clean jar runtimeJar
cd ../forbric-kernel-installer && ./gradlew standaloneJar
cp build/libs/forbric-server.jar /mnt/A/forbirckit/forbric-server.jar
rm -rf /mnt/A/forbirckit/.forbric-kernel/kernel
rm -f  /mnt/A/forbirckit/.forbric-kernel/lib/*/forbric-kernel*.jar
```

The server reads a **cached copy** under `.forbric-kernel/kernel/`, so skipping the two `rm` lines
runs the old jar and wastes a test round.

## 6. Suggested order

1. **P0-1 Adventure `Component` bridge** — unblocks the most plugins for the least new machinery
   (one serialise/parse pair, used by chat, action bar, titles, books).
2. **P0-2 `ItemMeta`** — the single highest-value object; needs the component mapping that P0-1
   also leans on, so the two share work.
3. **P0-4 container layer** — `InventoryView` + `openInventory` makes chest-type plugins possible.
4. **P1-6/7 `World` + `Player` gameplay** — broad but shallow; each method is a small mapping.
5. **P2** as reported by real plugins, not speculatively.

## 7. Diagnostic switches

| Property | Effect |
| --- | --- |
| `-Dforbric.logCommands=off` | stop logging every client command packet |
| `-Dforbric.vanillaClient=off` | stop admitting non-NeoForge clients in the configuration phase |
| `-Dforbric.playPayloadFallThrough=off` | leave play-phase payloads to NeoForge's dispatcher only |
| `-Dforbric.debug` | verbose `ForbricLog.debug` tracing |
